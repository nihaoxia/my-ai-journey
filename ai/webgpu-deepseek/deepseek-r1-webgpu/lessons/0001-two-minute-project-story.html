第一课：两分钟讲清项目

目标：不背宣传语，能从一次用户输入开始，顺着数据流解释到 GPU，再回到界面。

先记住一句话：这是一个把小型因果语言模型放进浏览器，用 Web Worker 承载 Transformers.js 推理，并通过 WebGPU 调用 GPU 的本地聊天 Demo。

1. 先画数据流

用户输入 → React state → postMessage(generate) → Worker 分词 → model.generate → WebGPU → TextStreamer → update 消息 → React 渲染

这是设计中的完整链路；最后一步的回答渲染尚未接通。浏览器里有两个分工：主线程照顾页面，Worker 承接推理任务；GPU 是执行模型计算的硬件资源。Worker 和 GPU 是两个不同概念。

推理是什么？使用已经训练好的模型产生输出。token 是模型处理的文本单位，不一定等于一个汉字或一个单词；tokenizer 把输入转成这些单位的编号，生成器逐步预测接下来的编号，再解码成文本。

库的分工：Transformers.js 提供加载、分词和生成接口，ONNX 是模型表示格式，ONNX Runtime Web 负责执行模型，WebGPU 提供浏览器访问 GPU 的接口。React 状态更新和普通分词代码仍由 CPU 执行，因此“全链路基于 WebGPU 加速”需要改为“模型推理使用 WebGPU 后端”。

加载阶段则是：load 消息 → 下载 tokenizer/ONNX 分片 → 进度回调 → 用 1 token 预热 → ready。

2. 面试口述稿

这个项目基于 Hugging Face 官方示例二次开发，目标是在浏览器本地运行 DeepSeek-R1-Distill-Qwen-1.5B。React 负责界面；Web Worker 承接模型加载、分词和文本生成。Transformers.js 加载 ONNX 模型，借助 ONNX Runtime Web 的 WebGPU 后端使用本机 GPU。输入先转换成 token 编号，模型逐步生成后续 token，再通过 TextStreamer 回传增量文本。主线程发送的命令用 type，Worker 回传的结果用 status。当前仓库已编写 Worker 侧推理流程和前端加载进度，但回答渲染与中断按钮还未接通。具体二次开发贡献需要结合自己的实际工作补充，不能把示例原有能力都算作个人设计。

证据入口：worker.js 第 15–36 行（模型加载）、第 52–57 行（输入模板）、第 84–123 行（流式消息及生成）；App.tsx 第 88–95 行（待实现消息处理）。下载本身是异步 I/O；Worker 主要隔离分词、生成调度等工作，不能把它简单说成“异步下载必须用 Worker”。

3. 主动回忆

不看上面的稿子，回答：为什么 Worker 能改善体验，但不能让 GPU 计算本身变快？

Worker 解决的是主线程被长任务占用的问题，保持界面响应；GPU 是否更快取决于模型规模、算子支持、显存/带宽、浏览器后端和编译开销。两者分别解决调度隔离和计算吞吐问题。

追问：q4f16 为什么可能降低资源占用？

量化减少权重每个参数所需的位数，f16 部分保留较高数值精度；权重体积和传输/显存压力通常下降，但实际速度和精度取决于算子与硬件支持。

4. 今天的边界

不要把“代码里发送了 update”说成“页面已经流式渲染”。面试官追问实现位置时，应指出 src/worker.js 发送消息，而 src/App.tsx 的对应分支目前为空。更多术语见 速查表，资料见 资源索引。
