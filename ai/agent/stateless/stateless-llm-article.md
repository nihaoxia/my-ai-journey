# 大模型为什么「不记得你」：从无状态 HTTP 到上下文工程的完整入门

> 本文基于当前目录里的 `readme.md` 和 `demo/index.mjs` 整理而成。主题很朴素：为什么大模型接口看起来像聊天，底层却像一个每次见面都要重新自我介绍的陌生人？

很多人第一次调用大模型 API 时，会有一种错觉：既然我在「聊天」，那模型应该记得刚才发生了什么吧？就像你和朋友微信聊了 20 分钟，突然问一句「我刚才说的那家火锅店叫什么」，对方大概率不会像刚重启的路由器一样沉默。

但大模型接口不是微信好友，也不是热心同事，更不是脑子里长了一个永久记事本的电子助理。它的底层更接近一次普通的 HTTP 请求：你发一份输入，它消耗算力生成一份输出，然后这次请求就结束了。下一次你再来，它不会天然继承上一次的记忆。换句话说，模型不是失忆，它只是从来没有被要求保存你的状态。

这就是本文的核心：**LLM 调用的本质是无状态的 HTTP 计算，所谓「连续对话」，本质上是客户端或业务系统每次把上下文重新塞进请求里。**

听起来有点反直觉，但理解了这一点，你就会突然看懂很多 AI 工程里的关键词：`messages`、`chatHistory`、Token 成本、上下文窗口、RAG、Skill、Agent、Loop Engineering、Harness。它们并不是一堆故作高深的黑话，而是在围绕同一个问题打转：**如何让一个无状态的模型，在有限成本内表现得像一个理解上下文的系统。**

## 一、先别急着问模型，先问 HTTP

在 Web 开发里，HTTP 协议天然就是无状态的。所谓无状态，可以简单理解为：

- 每次请求都是独立的。
- 服务器默认不依赖上一次请求。
- 请求里带了什么，服务器就知道什么。
- 请求里没带什么，服务器就当不知道。

比如你访问一个接口：

```http
GET /api/user/profile
Authorization: Bearer xxxxx
```

服务器之所以知道你是谁，不是因为它「记得」你刚才来过，而是因为你在请求头里带了身份信息。Cookie、Session、JWT、Authorization header，本质上都是在给无状态协议补一层「身份线索」。

这也是无状态架构能支撑高并发和高可用的重要原因。服务器不需要把每个用户的临时状态都抱在怀里，像幼儿园老师点名一样寸步不离。任意一台机器只要拿到完整请求，就能处理它。这样系统就容易水平扩展：加机器、做负载均衡、挂了自动切走，都比较自然。

如果服务器强依赖本地状态，事情就麻烦了。用户 A 的状态在机器 1 上，下一次请求却被负载均衡打到机器 2，机器 2 一脸无辜：「你谁？」这时就要做粘性会话、共享存储、状态同步，复杂度会一层层往上堆。

所以，无状态不是偷懒，而是一种工程取舍：**让请求自包含，让服务更容易扩展。**

## 二、LLM 也是无状态的，而且非常认真

当前项目的 `readme.md` 里有一句很关键的话：`llm也是无状态的 它基于http 每次请求独立`。

这句话值得刻在键盘旁边。大模型接口通常是这样的流程：

1. 客户端组织请求参数。
2. 把 `messages`、`model` 等内容发给服务端。
3. 服务端调度模型推理。
4. 模型根据这次请求里的上下文生成回答。
5. 服务端把结果返回给客户端。
6. 本次请求结束。

注意第 4 步：模型根据「这次请求里的上下文」生成回答。不是根据你昨天说过什么，不是根据你上一次 API 调用时发了什么，也不是根据你心里默念了三遍「它应该懂我」。

模型没有自动读取你的历史调用记录。它能看到什么，取决于你在当前请求里传了什么。你传得完整，它就显得聪明。你传得残缺，它就开始补脑。补得准叫推理，补得离谱叫幻觉。

所以很多新手会遇到一个现象：第一次告诉模型「我的名字叫零零发」，第二次直接问「我的名字是什么」，模型可能答不上来。不是因为模型智商下线，而是因为第二次请求如果没有带上第一次的内容，它根本看不到。

这就像你去窗口办事。第一次你说：「我叫零零发。」办事员点头。第二次你换了个窗口，什么证件也不带，直接问：「我是谁？」对方不报警已经很温柔了。

## 三、`demo/index.mjs` 到底演示了什么

项目里的 `demo/index.mjs` 用 OpenAI SDK 连接 DeepSeek 兼容接口，核心代码如下：

```js
const chatHistory = [
  { role: 'system', content: '你是一个严谨的助手' },
];

chatHistory.push({
  role: 'user',
  content: '请记住，我的名字叫零零发'
});
```

这里的 `chatHistory` 就是人工维护的上下文。它不是模型服务端自动保存的记忆，而是客户端手动保存的一组消息。

第一次请求：

```js
const response = await client.chat.completions.create({
  model: 'deepseek-chat',
  messages: chatHistory
});
```

模型收到的是：

- system：你是一个严谨的助手。
- user：请记住，我的名字叫零零发。

模型回答后，代码又把模型回复塞回 `chatHistory`：

```js
chatHistory.push({
  role: 'assistant',
  content: response.choices[0].message.content
});
```

这一步非常重要。很多人只保存用户消息，不保存模型回复，结果对话上下文少了一半。对模型来说，assistant 的历史回复同样是上下文的一部分。因为后续问题可能引用模型刚才的说法，比如「你刚才第二点展开讲讲」。如果你没把模型刚才的第二点放进下一次请求，它怎么展开？靠缘分吗？

第二次请求前，代码继续追加用户问题：

```js
chatHistory.push({
  role: 'user',
  content: '请问我的名字是什么？'
});
```

然后再次把完整 `chatHistory` 传给模型。这样模型才能看到前面那句「我的名字叫零零发」，于是就能回答出来。

这段代码展示了一个极其关键的事实：**连续对话不是模型自动连续，而是客户端不断把历史对话拼回去。**

## 四、`messages` 不是聊天记录那么简单

在 Chat Completions 这类接口里，`messages` 通常是一个数组，每条消息都有 `role` 和 `content`。常见角色包括：

- `system`：给模型设定身份、行为规则、输出风格和边界。
- `user`：用户输入的问题或指令。
- `assistant`：模型之前的回答。
- `tool`：工具调用结果，常用于 Agent 或函数调用场景。

从工程角度看，`messages` 是一次请求的「临时世界」。模型不会站在真实世界里回答你，它站在 `messages` 构造出来的世界里回答你。

如果 `system` 里写「你是一个严谨的助手」，模型就会倾向于更谨慎。如果 `user` 里写「请用三句话解释」，模型就会尽量压缩。如果历史消息里包含「用户名字叫零零发」，模型就会把它当作当前对话里的事实。

这也是 Prompt Engineering 的基本盘：你通过文本设计，让模型更容易理解任务。但注意，Prompt Engineering 只能提高抽到好结果的概率。项目笔记里有个很形象的说法：`prompt质量或设计只能提升抽到金卡，不是特别的可控`。

这句话很实在。好的 Prompt 像是在抽卡前洗手、点香、摆正手机，确实有帮助，但不能保证每次都出金。要提升可控性，不能只靠 Prompt，还要靠上下文组织、工具约束、流程闭环和结果校验。

## 五、chatHistory 的第一个坑：越聊越贵

既然每次都要手动带上完整历史，那问题来了：如果用户一直聊，`chatHistory` 会越来越长。

一开始只有几条消息：

```txt
system: 你是一个严谨的助手
user: 请记住，我的名字叫零零发
assistant: 好的，我记住了
user: 请问我的名字是什么？
```

聊 10 轮之后，消息可能有 20 多条。聊 100 轮之后，消息就开始像春节家庭群聊天记录一样，一眼望不到头。

这会带来几个问题：

1. **Token 成本上升。** 每次请求都要把历史消息重新发给模型，输入 Token 越来越多，账单也越来越有存在感。
2. **响应变慢。** 上下文越长，模型处理输入的时间通常越长。
3. **上下文窗口有限。** 模型能处理的 Token 有上限，不可能无限塞。
4. **噪声增加。** 很久以前的闲聊可能会干扰当前任务。
5. **维护困难。** 你需要决定哪些内容保留，哪些内容丢弃，哪些内容总结。

所以，`chatHistory` 不是一个可以无限 `push` 的许愿池。它更像一个背包：空间有限，带多了走不动，带少了会露宿街头。

## 六、chatHistory 的第二个坑：只保存用户消息不够

项目笔记里提到：`没有维护全部的history 大模型的回复也是关键`。

这是很多实现里的常见问题。有人只存用户问题，觉得模型回答反正是模型自己说的，下一次应该还知道。可惜模型没有这种「我刚才说过」的意识。对下一次请求来说，它看到的只有当前传入的 `messages`。

假设第一轮：

```txt
user: 帮我设计一个三层架构。
assistant: 可以分为 Controller、Service、Repository 三层。
```

第二轮用户问：

```txt
user: 第二层再详细讲讲。
```

如果你没有把 assistant 的上一条回复带上，模型可能不知道「第二层」指什么。它可能猜是网络协议第二层，也可能猜是蛋糕第二层，虽然蛋糕也不错，但产品经理大概率不会买账。

因此，一个基本原则是：**用户消息和模型回复都属于对话历史。**

## 七、LRU：让最近的上下文优先活下来

当 `messages` 越来越长时，最直接的办法是裁剪。项目笔记里提到 `LRU 缓存`、`最近聊的一定要留下，久远的要适当地删除`。

LRU 是 Least Recently Used 的缩写，意思是「最近最少使用」。在缓存系统里，它通常表示：空间不够时，优先淘汰最久没被访问的数据。

放到对话上下文里，可以理解为：

- 最近几轮对话通常最重要。
- 当前任务相关内容必须保留。
- 很久以前且不再相关的信息可以删除或压缩。
- 系统规则、用户偏好、任务目标不能轻易丢。

一个简化策略可以这样设计：

```txt
最终 messages = system 规则
             + 用户长期偏好摘要
             + 当前任务摘要
             + 最近 N 轮完整对话
             + 本次用户输入
```

这比简单粗暴地保留全部历史更靠谱，也比无脑截断前半段更稳。因为有些早期信息非常关键，比如用户最初定义的目标、约束和验收标准。如果直接删掉，模型就可能开始自由发挥。自由发挥在脱口秀里是才华，在工程里往往是事故预告。

## 八、从 Prompt Engineering 到 Context Engineering

项目笔记里写了一个升级路线：

- Prompt Engineering：聊天对话为主。
- Context Engineering：上下文工程。
- RAG：给模型补外部知识。
- Skill：沉淀可复用能力。
- Loop Engineering：循环工程。
- Harness：AI 工程。

这条路线很有价值，因为它把「会写提示词」和「会做 AI 应用」区分开了。

Prompt Engineering 关注的是怎么把一句话写得更清楚。比如：

```txt
请用通俗语言解释 LLM 的无状态机制，并给出 JavaScript 示例。
```

Context Engineering 关注的是：模型在回答前应该看到哪些材料，材料如何排序，哪些是强约束，哪些是参考信息，哪些需要摘要，哪些需要丢弃。

它解决的问题不是「这一句话怎么写」，而是「整个输入上下文怎么组织」。这就像做饭。Prompt 是调料，Context 是食材、锅、火候和菜谱。你不能拿一瓶好酱油去拯救一锅放了三天的面条。

## 九、RAG：当模型不知道，就别逼它编

LLM 的训练知识不是实时数据库，也不是你公司内部 Wiki。它可能不知道你的项目结构、业务规则、最新文档，更不知道你刚写在本地文件夹里的内容。

这时就需要 RAG，也就是 Retrieval-Augmented Generation，检索增强生成。它的基本思路是：

1. 用户提出问题。
2. 系统从知识库、文档、数据库或代码库中检索相关内容。
3. 把检索结果作为上下文传给模型。
4. 模型基于这些材料回答。

RAG 的价值不是让模型「变聪明」，而是让模型「有资料可查」。没有资料时，模型像闭卷考试；有 RAG 时，模型像开卷考试。开卷不保证满分，但至少不用现场发明教材。

在当前项目语境里，`readme.md` 就是一份小型知识库，`demo/index.mjs` 是可执行思路的证明。如果要做成一个更完整的 AI 应用，可以把项目文档、历史对话摘要、业务规则、用户资料都纳入检索范围，然后按相关性喂给模型。

## 十、Skill：把经验从一次性 Prompt 变成可复用能力

Skill 可以理解为更结构化、更可复用的上下文能力。普通 Prompt 往往是临时写的，像便利贴。Skill 更像一份操作手册，告诉模型在某类任务中应该遵循什么流程、读哪些资料、输出什么格式、避免哪些坑。

比如你经常让模型写技术文章，就可以沉淀一套写作 Skill：

- 先阅读项目文件。
- 提取核心概念和代码路径。
- 判断目标读者。
- 设计文章结构。
- 用通俗比喻解释抽象概念。
- 提供代码示例和工程实践。
- 最后检查术语、排版和事实一致性。

这样做的好处是，你不用每次都把流程从头打一遍。更重要的是，它降低了随机性。模型不再只是「根据一句话发挥」，而是按一套稳定流程完成任务。

## 十一、Loop Engineering：让模型不只回答一次

很多 AI 应用的问题不在于模型不会回答，而在于它只回答一次。真正复杂的任务往往需要循环：

1. 生成初稿。
2. 检查问题。
3. 修正错误。
4. 再次验证。
5. 必要时继续迭代。

这就是 Loop Engineering 的价值。它把模型从「一次性输出机器」变成「可迭代执行单元」。

以当前示例来说，如果只是问模型「解释无状态」，它会给一段答案。但如果做成循环工程，可以让系统执行：

- 读取 `readme.md` 和代码。
- 提取知识点。
- 生成文章大纲。
- 根据大纲写正文。
- 检查是否覆盖无状态、`messages`、Token、LRU、RAG 等主题。
- 检查是否达到字数要求。
- 检查 Markdown 格式。
- 修订不清楚的段落。

这就从「问答」升级成了「工作流」。两者差别很大。问答像点外卖，工作流像后厨真的在切菜、下锅、试味、装盘。

## 十二、Harness：把 AI 放进工程笼子里

Harness 这个词可以理解为「测试夹具」或「执行框架」。在 AI 工程里，它强调的是：不要把模型当作一个孤零零的黑盒，而要用工程系统包住它。

一个可靠的 AI Harness 往往包括：

- 输入构造：如何生成 `messages`。
- 上下文管理：如何裁剪、摘要和检索。
- 工具调用：模型什么时候能查数据库、读文件或调用 API。
- 结果校验：输出是否符合格式、事实和业务规则。
- 错误处理：超时、限流、空回复、JSON 解析失败怎么办。
- 观测指标：Token 用量、延迟、成功率、重试次数。
- 安全边界：哪些数据不能发给模型，哪些操作必须确认。

没有 Harness 的 AI 应用，就像把一台发动机直接焊在自行车上。它可能跑得飞快，也可能在第一个路口表演物理学。

## 十三、工程落地：一个更靠谱的上下文管理方案

如果要把当前 demo 扩展成一个真实应用，可以按下面的思路升级。

第一步，保留固定的系统规则：

```js
const systemMessage = {
  role: 'system',
  content: '你是一个严谨的助手，回答必须基于已提供的上下文。'
};
```

第二步，维护完整原始历史，但不要每次全部发送：

```js
const fullHistory = [];
```

第三步，每次请求前构造精简上下文：

```js
function buildMessages({ summary, recentMessages, currentInput }) {
  return [
    systemMessage,
    { role: 'system', content: `当前对话摘要：${summary}` },
    ...recentMessages,
    { role: 'user', content: currentInput }
  ];
}
```

第四步，设置容量策略：

- 最近 5 到 10 轮完整保留。
- 更早内容压缩成摘要。
- 用户偏好和任务目标单独保存。
- 关键事实不要只靠自然语言历史埋着，最好结构化存储。

第五步，必要时接入 RAG：

- 用户问项目相关问题时，检索代码和文档。
- 用户问业务规则时，检索知识库。
- 用户问历史决策时，检索会议记录或需求文档。

这样系统就不会只是「把聊天记录越堆越高」，而是在认真管理上下文资产。

## 十四、几个常见误区

**误区一：模型会自动记住用户信息。**

不会。除非平台提供了独立的记忆功能，或者你自己把信息保存并在后续请求中带上，否则模型看不到。

**误区二：`chatHistory` 越完整越好。**

不一定。完整历史会增加成本和噪声。好的上下文管理不是全部保留，而是该留的留，该删的删，该总结的总结。

**误区三：只要 Prompt 写得好，一切都能解决。**

Prompt 很重要，但它不是魔法。复杂任务需要检索、工具、循环、校验和状态管理。

**误区四：RAG 就是把文档一股脑塞进去。**

不是。RAG 的重点是检索相关内容，而不是搬家式投喂。喂太多无关资料，模型也会消化不良。

**误区五：无状态代表不能做连续对话。**

无状态只是说服务端不默认保存状态。连续对话当然能做，但状态要由客户端、业务服务、数据库或专门的上下文系统来维护。

## 十五、把这件事讲透：模型不是记忆体，而是计算器

一个很实用的心智模型是：**把 LLM 当作高级文本计算器，而不是自动记忆体。**

你给它输入，它给你输出。你希望它基于历史回答，就把历史放进输入。你希望它参考知识库，就把检索结果放进输入。你希望它遵守规则，就把规则放进输入。你希望它别乱来，就用校验和工具边界约束它。

当你这样理解后，AI 工程就清楚多了：

- `messages` 是输入载体。
- `chatHistory` 是客户端维护的历史。
- Token 是上下文预算。
- LRU 是预算不足时的取舍策略。
- RAG 是外部知识补给。
- Skill 是可复用任务流程。
- Loop Engineering 是迭代执行能力。
- Harness 是把这些能力工程化的外壳。

这条线串起来，所谓「智能应用」就不再神秘。它不是把一个大模型接口接上前端页面就完事，而是围绕无状态模型搭建一整套上下文、工具、流程和验证系统。

## 结语：让无状态模型干有上下文的活

当前项目虽然文件不多，但抓住了 LLM 工程里一个很核心的问题：大模型接口本质上是无状态调用，而我们想要的却是有上下文、有记忆、有目标、有连续性的智能体验。

这中间的差距，就是 AI 应用开发真正要解决的问题。

最朴素的 demo 里，`chatHistory.push()` 已经揭示了答案：模型不是自己记住了你，而是我们每次把该记住的东西重新告诉它。再往前走，就会自然演化出上下文工程、摘要压缩、LRU 裁剪、RAG 检索、Skill 复用、循环执行和 Harness 约束。

所以，下次模型忘了你是谁，先别急着怪它冷漠。它只是严格遵守了无状态协议。真正该反思的是：我们有没有把「你是谁」这件事，作为上下文的一部分，好好地交到它手里。

说到底，LLM 应用开发的第一课不是「如何写一个惊艳的 Prompt」，而是「如何管理上下文」。Prompt 决定你怎么开口，上下文决定模型到底听见了什么。前者像说话技巧，后者像带没带资料。只会说漂亮话但资料没带，全场最会表达的人也只能现场编。

而工程师的任务，就是别让模型现场编。
